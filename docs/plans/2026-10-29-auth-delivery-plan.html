We will finish the auth service in this repo before we start the Swift app. We will deliver one reviewed change at a time, beginning with the session boundary. The web must remain usable after every merge. The first database change waits for compatibility evidence and a usable recovery procedure.

The approved design explains the intended behavior. The native app owns Face ID unlocks and their fallback behavior. This plan covers the server work needed to support that app's later login.

What finished means

The web signs existing users in through Better Auth without changing their identity, password or financial records. It keeps its current idle behavior, signup controls and onboarding. A test native client can complete login, renew access, and call a protected endpoint that identifies its own user.

We hand the mobile repo a tested auth contract and recovery instructions. Expense APIs, mobile screens and Face ID implementation belong to the mobile phase. We will define those APIs when we know the first mobile journey.

Removing the old password storage is a separate, delayed step. It does not block mobile development while the compatibility storage remains safe.

Preparation before a database change

The compatibility work resolves technical questions with primary documentation and isolated local proof. It chooses an exact compatible library version and records which behavior we tested. We do not add production tables based on an unverified schema or a library-version assumption.

The recovery work documents what Christian can restore, how long the recovery window lasts, and how to put the app back into service. It includes a rehearsal with invented data. An agent never restores or queries the production database.

Acceptance checklist for preparation
  • Verify the selected Better Auth core and OAuth provider versions against current official documentation, release dates and the repo's Prisma version. ADR-0027 currently requires a 1.7.x release at least two weeks old. If evidence conflicts with that constraint, stop for an authorized ADR amendment.
  • Prove legacy bcrypt hashes and short existing passwords work without weakening signup's strength rules. Verify mapping to the existing User model and UUID identity format.
  • Prove gated signup, the cap and starter-account provisioning remain safe through every public provider endpoint. Resolve transaction or retry behavior.
  • Prove explicit idle renewal, passive reads and late renewal races against the selected version. Decide how session caching affects revocation.
  • Choose a rollback-safe policy for every password writer, including signup, provisioning, seed, change password and manual reset. Prefer proving atomic credential mirroring; do not assume a post-write hook gives atomicity.
  • Resolve the conflict between CHORE-33's existing Auth.js brief and spec 0009. This plan does not implement CHORE-33. If it lands first, preserve its contract; otherwise propose a separate Better Auth brief for it. Do not discard the owner's earlier password-change decisions as a side effect of this migration.
  • Document the actual Neon recovery window with an account-specific check performed or supplied by Christian. Do not infer it from an advertised plan name.
  • Restore an invented-data backup locally, verify its records, and document how deployment configuration and database recovery differ.

Web migration

The storage expansion adds auth tables and compatible user fields without switching login. Its tests compare existing users and financial rows before and after the migration. The owner can keep the old app running on that schema.

The next slice copies credentials and switches the web. It preserves closed signup, onboarding, translated errors, idle expiry and logout. We test rollback after creating an account and changing a password during the transition.

Acceptance checklist for the web migration
  • Expansion changes no financial table, user identity or financial foreign key. Existing password hashes stay intact; the old login continues to work.
  • The credential copy runs once per eligible user, inside a transaction, and safely repeats. Per-user guards reject missing, duplicate or mismatched credentials. Aggregate counts are only supporting evidence.
  • Every password-writing route follows the compatibility policy proven in preparation. Rolling back does not lose new accounts or changed passwords.
  • Existing login, logout, signup gate and cap, onboarding, name refresh, expiry notices and cross-tab behavior pass automated and real-browser checks.
  • Database-backed rate limiting works across separate server instances. State the database-unavailable behavior; do not silently allow requests.
  • The migration runbook includes preflight and post-deploy surveys, rollback targets and stop conditions. Production checks belong to Christian.
  • Record the actual production switch date. Start the observation clock from that deployment, not a local test or PR creation date.

Native authorization and handoff

We first enable the standard native login protocol and verify it with an invented test client. We then add the smallest protected identity endpoint needed to prove the server accepts the resulting access credentials.

This establishes the auth contract before the Swift app exists. It does not require a dashboard or an expense API. Final app identifiers and callbacks must come from the mobile repo; production registration cannot use placeholders.

Acceptance checklist for native authorization
  • Verify authorization code with S256 PKCE for a public client without a secret. Enforce exact redirects, consent policy, supported scopes and discovery metadata.
  • Test wrong verifier, wrong redirect, code reuse and invalid client requests. Use a disposable local client and invented users; register production identifiers only when the mobile repo supplies them.
  • Settle explicit access and refresh lifetimes and renewal limits. Prove that web idle expiry does not unintentionally prevent persistent mobile sign-in.
  • Test refresh rotation, reuse policy, concurrent requests, lost responses, explicit logout and password-revocation behavior for the selected version.
  • Choose the token-validation and revocation strategy together. If JWT access tokens remain usable until expiry, document and agree on that window before claiming all-device revocation. Include signing-key rotation and verification failures.
  • A bounded identity route, tentatively GET /api/v1/me, returns only the authenticated user's allowed identity fields. It checks signature, issuer, audience, expiry and required scopes, and refuses ID tokens or caller-supplied identity.
  • The client contract documents endpoints, error responses, scopes, PKCE, callbacks, secure token storage expectations, refresh and revocation behavior. Verify an end-to-end token exchange and protected request against that contract.

Cleanup after observation

Keep the compatibility storage for at least two weeks of normal production use. Remove it only when account surveys are clean and recovery is ready. The cleanup must not remove data that the active app or a supported recovery path still needs.

How each slice runs

The main session owns the plan, acceptance criteria and handoffs. An implementer subagent owns code changes and checks. A fresh reviewer subagent inspects the actual diff without receiving the implementer's conclusions. Confirmed findings go back to the implementer, with at most two repair rounds.

After the checks and review pass, we report the result before moving to the next slice. Commits and pushes require Christian's explicit instruction. Christian merges; we do not approve or merge PRs or push to main.
